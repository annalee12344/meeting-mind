# Meeting Mind — Storage & Data Architecture Foundation

This document specifies the data foundation and storage architecture of Meeting Mind, designed to allow future integration of databases, user authentication, and meeting history by swapping only the storage adapter.

---

## 1. Architectural Philosophy: Two Decoupled Data Layers

Meeting Mind separates raw AI analysis from human edits into two distinct, independent layers:

```
┌────────────────────────────────────────────────────────┐
│               Immutable AI Layer                       │
│  - Pipeline output (MeetingOutput)                     │
│  - Re-runnable, prompt-upgradeable, cached             │
│  - Stable UUIDs generated by backend                   │
└──────────────────────────┬─────────────────────────────┘
                           │
                           ▼   Pure Merge Function
                    merge_meeting_view()
                           ▲
┌──────────────────────────┴─────────────────────────────┐
│                 Mutable User Overlay                   │
│  - Granular edits (MeetingOverlay)                     │
│  - Task done/undone, title/assignee/deadline edits     │
│  - Manual tasks, converted unresolved tasks            │
│  - Issue status & user notes (IssueNote)               │
└────────────────────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────────┐
│            Unified View Model (MeetingViewModel)       │
│  - Single model consumed by all UI components          │
│  - Idempotent: re-analyzing transcript never wipes     │
│    user modifications                                  │
└────────────────────────────────────────────────────────┘
```

### 1.1 The Immutable AI Layer (`MeetingOutput`)
- Produced by the 4-step pipeline: `Step 0: Tagging` $\rightarrow$ `Step 1: Extractor` $\rightarrow$ `Step 2: Resolver` $\rightarrow$ `Step 3: Validator` $\rightarrow$ `Step 4: Mapper`.
- Schema:
  - `summary: str`: High-level meeting summary.
  - `participants: list[str]`: Meeting attendees.
  - `decisions: list[PublicDecision]`: Confirmed decisions (superseded ones remain only in `history`).
  - `tasks: list[PublicTask]`: Assigned and confirmed tasks with ISO deadlines.
  - `unresolved: list[PublicUnresolvedItem]`: Open decisions and unconfirmed tasks.
  - `issues: list[PublicIssue]`: Blockers and technical hurdles.
  - `meta: PublicMeta`: Hashes, models, meeting dates, prompt versions.
- **Idempotence Guarantee:** If a user re-analyzes a meeting or upgrades LLM prompts, the AI layer is regenerated without touching the user's overlay.

### 1.2 The Mutable User Overlay (`MeetingOverlay`)
- Schema:
  - `meeting_id: str`: Unique meeting identifier or transcript hash.
  - `tasks: dict[str, TaskOverlay]`: Modifications indexed by Task UUID (title, assignee, deadline, status, completed_at).
  - `manual_tasks: list[ViewTask]`: User-created tasks not present in transcript.
  - `deleted_task_ids: list[str]`: Tasks deleted by user.
  - `unresolved: dict[str, UnresolvedOverlay]`: Unresolved modifications (status="converted", converted_to_task_id).
  - `deleted_unresolved_ids: list[str]`: Unresolved items dismissed.
  - `issues: dict[str, IssueOverlay]`: Issue modifications (status="open" | "resolved").
  - `issue_notes: list[IssueNote]`: Notes attached to issues with author ID and timestamp.
  - `deleted_issue_ids: list[str]`: Issues deleted by user.

### 1.3 Pure Merge Function (`merge_meeting_view`)
Implemented identically in Python (`pipeline/overlay.py`) and TypeScript (`meeting-muse-56/src/lib/overlay.ts`):
- O(1) exclusion of deleted IDs.
- Overlays title, assignee, deadline, and done status over AI tasks.
- Appends user-created manual tasks and converted unresolved items.
- Overlays issue statuses and groups `issue_notes` by `issue_id`.

## 2. Stable IDs and Lineage Tracking

1. **UUIDv4 Identity:** Every entity (`PublicDecision`, `PublicTask`, `PublicUnresolvedItem`, `PublicIssue`, `Evidence`, `IssueNote`) receives a backend-generated UUID (`id`).
2. **LLM Reference Decoupling:** LLM tags (`A001`, `D001`, `U001`) are retained strictly as `source_ref` for auditing, evidence citations, and UI badges. They are never used as primary keys.
3. **Cache Persistence:** When results are retrieved from cache or precomputed samples, all item UUIDs are preserved deterministically.

## 3. Storage Abstractions

### 3.1 Backend Abstractions
- **`AnalysisCache` (`pipeline/cache.py`):**
  - Thread-safe in-memory cache with LRU eviction and configurable TTL (default 24h).
  - Cache key is generated using Unicode NFC-normalized transcript hash, meeting date, threshold, and prompt version.
- **`JobStore` (`pipeline/job_store.py`):**
  - Thread-safe job store managing asynchronous analysis jobs.
  - Automatic TTL expiration (default 30 minutes) and capacity bounds (100 jobs).
  - Tracks discrete pipeline stages: `queued` $\rightarrow$ `preprocessing` $\rightarrow$ `extracting` $\rightarrow$ `resolving` $\rightarrow$ `validating` $\rightarrow$ `mapping` $\rightarrow$ `done` | `failed`.
  - Supports non-blocking job cancellation (`cancel_job`).

### 3.2 Frontend Abstraction (`PersistenceAdapter` in `src/lib/storage.ts`)
```typescript
export interface PersistenceAdapter {
  loadOverlay(meetingId: string): Promise<MeetingOverlay | null>;
  saveOverlay(overlay: MeetingOverlay): Promise<void>;
  deleteOverlay(meetingId: string): Promise<void>;
  listOverlays(): Promise<Array<{ meetingId: string; updatedAt: string }>>;
}
```

#### Implementations:
1. **`LocalStorageAdapter` (Active):**
   - Key format: `mm_overlay_{meeting_id}`.
   - Comprehensive error guards with `QuotaExceededError` handling: automatically prunes the oldest meeting overlays if browser quota is reached.
2. **`ApiAdapter` (Swappable Skeleton):**
   - Implements `PersistenceAdapter` pointing to `/api/v1/meetings/:id/overlay`.
   - Ready to swap in when a multi-user backend (PostgreSQL/SQLite) is deployed.
   - Switch via `setDefaultPersistenceAdapter(new ApiAdapter('/api/v1'))`.

## 4. Asynchronous Job Processing

1. **Job Dispatch:** `POST /api/v1/analyze` creates a background job and immediately returns `job_id`, `stage`, and `poll_url`.
2. **Real-time Tracking:** Client polls `GET /api/v1/jobs/{job_id}` at 500ms intervals.
3. **Step-by-Step UI:** Replaces the legacy fake timer with actual pipeline stages:
   - `Bước 0: Tiền xử lý & gán mã phát biểu [U001]`
   - `Bước 1: Trích xuất phát biểu then chốt (Gemini)`
   - `Bước 2: Phân nhóm chủ đề & tiến trình thay đổi (Gemini)`
   - `Bước 3: Xác minh bằng chứng RapidFuzz`
   - `Bước 4: Chuẩn hóa cấu trúc 4 nhóm dữ liệu`
4. **Cancellation:** `POST /api/v1/jobs/{job_id}/cancel` terminates or flags the task, resetting the client interface cleanly.

## 5. Export, Import & Migration

### 5.1 Export Package Format (`ExportPackage`)
When users export a meeting to JSON, it bundles both data layers into a versioned package:
```json
{
  "schema_version": "2.0.0",
  "exported_at": "2026-10-14T10:00:00Z",
  "meeting_name": "Sprint 24 Planning",
  "transcript": "[09:00] ...",
  "result": { ... },
  "overlay": { ... }
}
```
**User Edit Preservation:** Re-importing this package completely restores all user edits, assignments, done statuses, and issue notes.

### 5.2 Legacy 5-Array Format Migration
Older exported files (containing `action_items`, `blockers`, `requests`, `unresolved_items`) are automatically recognized upon import:
- Client routes legacy JSON to `POST /api/v1/legacy/upgrade`.
- Backend mapper upgrades the schema into modern `MeetingOutput`.
- Client opens the upgraded meeting without data loss.

## 6. Current Operating Limits & Future Roadmap

> [!NOTE]
> **Browser-Only Storage Limit:** In the current local test environment without a database, user overlays live exclusively in that specific browser's `localStorage`. Opening the application in a different browser, incognito mode, or another computer will not show prior edits unless transferred via JSON export/import.

> [!NOTE]
> **Backend Process Lifecycle:** The backend `JobStore` and `AnalysisCache` are in-memory. Restarting the FastAPI server clears active/cached jobs.

### Swapping to a Database (Future Step):
Adding PostgreSQL or SQLite requires only:
1. Creating DB tables matching `models/overlay.py` (`tasks`, `overlays`, `issue_notes`).
2. Implementing a backend repository implementing the `MeetingOverlay` schema.
3. Activating `setDefaultPersistenceAdapter(new ApiAdapter())` on the frontend.
No UI components or pipeline modules need to change.
